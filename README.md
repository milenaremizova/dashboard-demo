# Dashboard

Внутренний дашборд статистики платформы компании - транзакции, регистрации, обработка заявок (автоматические/ручные зачисления). Может масштабироваться и на другие метрики. Автоматизирована ручная работа - крон-скрипт собирает данные из БД и выводит на дашборд.
В проекте представлена демо-версия. 

Общие возможности: тотал по каждой метрике, сравнительная статистика (от 2-х дней) по дням/неделям/месяцам/произвольному диапазону, в виде диаграмм.

Депозиты: ручное изменение кол-ва выполненных заданий с лейблом "ручное", перерасчёт тоталов и сравнительной статистики с учётом правок. Настройка самих заданий (taskId/суммы) - через интерфейс, без изменений в коде.

Обработка заявок: сравнение автоматических и ручных зачислений по категориям в виде таблицы по неделям (минимальный период - неделя) и графика динамики по дням.

## Стек

**Frontend:**
- React + TypeScript + Vite
- Recharts - графики (бар-чарт, составной график с двумя Y-осями)
- react-day-picker + @floating-ui/react - кастомный дейтпикер, стилизован под тему, адаптивное позиционирование попапа
- date-fns - локализация дейтпикера (русская локаль)
- lucide-react - иконки
- Inline-стили (CSSProperties) + CSS-классы в global.css для того, что инлайн не делает (:hover, :nth-child, @media). Цвета/шрифты - через CSS-переменные (--color-*, --font-*), выставляются один раз на корне через themeVars(), дальше доступны и в JS (COLOR.*), и в обычном CSS (var(--color-*)) - единый источник правды, без дублирования

**Backend:**
- Node.js + Express, plain JS (без сборки/компиляции)
- pg - подключение к БД, read-only
- node-cron - расписание сборщиков
- Хранение - JSON-файлы на диске (`data/<metric>-stats.json`), без отдельной БД под сам дашборд - оправдано объёмом данных (пара метрик × сотни дней)

> В этом репозитории - демо-режим (`DEMO_MODE=true` в `.env`): реального подключения к БД нет, крон-сбор новых данных отключён, дашборд работает на заранее подготовленном наборе данных в `data/`. Вся остальная архитектура (роуты, авторизация, ручные корректировки) рабочая, без заглушек - `DEMO_MODE` отключает только автосбор. Для сохранения конфиденциальности.

**Авторизация/безопасность:**
- Общий API-ключ через заголовок Authorization
- CORS ограничен списком origin через `ALLOWED_ORIGINS`

## Файловая структура

```
dashboard/
    dashboard-frontend/ ← React + TS + Vite
    dashboard-backend/ ← Node + Express (plain JS)
```

Два независимых сервиса, имеют свои .env. Коммуникация по HTTP: фронтенд ходит на бэкенд за данными.

## Запуск

Необходим Node.js.

### 1. Backend

```bash
cd dashboard-backend
npm install
cp .env.example .env
npm run dev
```

### 2. Frontend

```bash
cd dashboard-frontend
npm install
cp .env.example .env
npm run dev
```

Оба сервиса должны быть запущены одновременно, в двух отдельных терминалах.

## Backend

### Архитектура: метрики через реестр сборщиков

Каждая метрика (депозиты, регистрации, обработка заявок) - независимый модуль в `metrics/<name>/`:

```
metrics/
    deposits/
        collect.js ← SQL-запрос к БД + сборка дня
        routes.js ← Express-роут, отдаёт данные фронту + настройку тиров
        sumMappingStore.js ← чтение/запись sumMapping.json, вынесено отдельно, тк используется и collect.js, и роутами настройки тиров
        config/
            sumMapping.json ← актуальные задания недели, требуют ручной актуализации (минимально)
    registrations/
        collect.js
        routes.js
    task-credits/
        collect.js ← отдельный запрос по каждой категории (progress = 100 - автоматически, progress < 100 - вручную)
        routes.js
        config/
            games.js ← список категорий, не ротируется как задания, поэтому просто статичный список, без отдельного JSON под еженедельные правки
```

Общий код (не завязанный на конкретную метрику) - в корне бэка:
- `db.js` - read-only pool-подключение к БД (только `SELECT`)
- `storage.js` - чтение/запись `data/<metric>-stats.json`, обобщено по `metricKey`
- `cron/collectors.js` - реестр всех метрик: `{ key, collect }[]`.
- `schedule.js`/`backfill.js`/`catchup.js` - единственное место, которое знает про все метрики разом: перебирают его, а не завязаны на конкретную метрику

Для разового сбора сегодняшнего дня без ожидания ближайшего срабатывания таймера - `collect-today.js` в корне бэка (`node collect-today.js`).

### Хранение данных

`data/<metric>-stats.json` - один файл на метрику, JSON. У каждой метрики свой JSON.

```json
{
  "dailyStats": { "2026-09-16": { ... } },
  "overrides": { "day:2026-09-16_2026-09-16::sum_1000": 12 }
}
```
Каждый день записывается один раз и больше не пересчитывается задним числом. Это сделано, чтобы при смене `sumMapping.json` прошлые дни сохраняли то название/сумму, что было актуально на момент сбора. Такой подход позволяет хранить данные по всем неделям.

Бэкапы - `data/backups/`, снимок раз в сутки (внутри ночной cron-задачи), хранится последние 30.

### Cron-расписание (`cron/schedule.js`)

- **`10 0 * * *`** (00:10 ночью) - финализирует вчерашний, уже закрытый день + делает бэкап.
- **`*/30 * * * *`** (каждые 30 мин) - пересобирает сегодняшний, ещё не закрытый день, чтобы на дашборде были не только "вчера и раньше", а динамичные цифры за сегодня. Также после редакции заданий через модальное окно изменения вступят после ближайшей работы крона.

`cron/catchup.js` при каждом старте сервера проверяет последние 30 дней и дособирает то, что пропустил, пока сервис не работал (в процессе разработки ноутбук был выключен и т.п.).

### Еженедельные задания: `sumMapping.json`

Задания на платформе меняются каждую неделю - меняются `task_id`. Каждую неделю нужно обновлять через интерфейс дашборда - шестерёнка на панели заданий открывает форму (code/taskId/название/сумма, добавление/удаление строк, сохранение шлёт `PUT /api/deposits/tiers`). Так актуализация не требует похода в код и на сервер.
```json
{
  "sum_1000": { "taskId": 8758, "name": "Игровая сборка", "amount": 1000 }
}
```
- ключи (`sum_1000` и т.п., он же `tierCode`) - **никогда не меняются**, это стабильный идентификатор тира. Если на новой неделе стало меньше/больше заданий, можно удалить/добавить строку полностью, но не менять код суммы.
- `taskId`/`name`/`amount` - обновляются под текущую неделю. Amount - предпочтительнее неизменно, при возможности актуализации подвергать только taskId и name, сопоставляя коды сумм с актуальными заданиями.


⚠️ `taskTiers.ts` на фронте - только добавлять новые задания, никогда не удалять существующие, даже если квест временно неактивен (иначе пропадёт историческое отображение).

### Авторизация

Простая защита общим ключом - не полноценная авторизация с пользователями, но закрывает доступ к API для посторонних в сети. Все роуты под `/api` требуют заголовок: Authorization: Bearer <API_KEY>

Без него будет `401 Unauthorized`. Ключ хранится в `.env` бэка (`API_KEY`) и фронта (`VITE_API_KEY`), они должны совпадать один в один.

Дополнительно CORS ограничен списком origin через `ALLOWED_ORIGINS` в `.env` бэка. При демонстрации по локальной сети нужно временно добавить туда IP фронта.

`metrics/deposits/`, `metrics/registrations/` и `metrics/task-credits/` специально зеркалят друг друга по структуре и именам файлов там, где это применимо. Добавление новой метрики в будущем - это копирование той же схемы папок с новым содержимым внутри, без создания новой структуры, только добавление уникальных компонентов, если того требует метрика.

### Режимы данных

`VITE_USE_MOCK_DATA` в `.env`:
- `true` генерирует моки локально, хранит в `localStorage` (без бэкенда)
- `false` ходит на `VITE_API_BASE_URL` с `VITE_API_KEY` в заголовке

### Адаптив

Базовая мобильная адаптация есть (карточки/шапка/периоды складываются в колонку, логотип и шрифты уменьшаются на узких экранах через медиа-запрос max-width: 480px). Дашборд рассчитан на десктоп, однако поддерживается мобильная версия для адаптива.

## Демонстрация в локальной сети

Для разового показа без деплоя:
```bash
# бэкенд — без изменений
npm run dev

# фронтенд с флагом --host для просмотра по локальной сети
npm run dev -- --host
```
`.env` фронта временно указывает на IP вместо `localhost` (`ipconfig` → `IPv4 Address`), в `.env` бэка в `ALLOWED_ORIGINS` тоже нужно временно добавить этот IP. После показа необходимо остановить оба процесса, вернуть оба `.env` на `localhost`.
